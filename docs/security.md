# Security

Weft Sandboxes exists to run code you do not trust, often written by an AI
model, next to data you care about. This page describes what it defends
against, how, and where the limits are. To report a vulnerability, see
[SECURITY.md](../SECURITY.md).

## Threat model

**The attacker** controls everything inside one sandbox: the code, the root
account in the guest, the guest's view of its devices and the network traffic
it sends. They may also hold a team API key.

**They must not be able to:**

1. Run code on the host, or read or change another sandbox.
2. Reach the EC2 instance metadata service, the host agent, the control plane,
   other AWS services or anything in your VPC that the team's egress policy
   does not allow.
3. Send data anywhere the egress policy does not allow, including through DNS.
4. Read the credentials the credential proxy injects.
5. Use a team API key to see or affect another team's sandboxes, templates or
   policies.
6. Deny service to other sandboxes beyond their own resource limits.

**Out of scope:** a malicious stack administrator, compromise of your AWS
account or of AWS itself, and physical attacks. Speculative-execution side
channels are mitigated (SMT disabled on hosts, Firecracker's guidance) but not
eliminated.

## Isolation layers

A sandbox escape has to get through all of these.

| Layer | What it does |
| --- | --- |
| **KVM and Firecracker** | Every sandbox is a microVM with its own kernel. Firecracker has a minimal device model (virtio network, block and entropy devices and a serial console here) and runs with its default seccomp filters |
| **Jailer** | Each Firecracker process runs chrooted, as its own UID and GID (`uid_base + slot`, never root), in a new PID namespace and in the sandbox's network namespace, with cgroup v2 limits on memory, CPU and PIDs, and file size and open-file limits |
| **Rate limits** | Per-VM limits on network, disk, entropy and console output |
| **Network namespace per sandbox** | The guest's tap device lives in a namespace of its own, with IPv6 disabled. Its firewall rejects link-local destinations (including the metadata service at `169.254.169.254`), sends DNS to the host's resolver, forwards only TCP (which the host redirects to its egress forwarder) and drops everything else |
| **Egress gateway** | Checks every connection and HTTP request against the sandbox's policy. It also checks that the connection comes from the host running that sandbox, so a host cannot claim another host's sandbox |
| **DNS allowlist** | Names outside the policy get `NXDOMAIN`, so DNS cannot carry data out |
| **Host** | IMDSv2 only, hop limit 1, instance tags hidden from metadata. No SSH; operators use Session Manager. The host's IAM role has no access to S3, DynamoDB, ECR or Secrets Manager |

The guest kernel is built from a pinned Linux LTS release with a minimal
configuration: no loadable modules, and VMGenID plus virtio-rng so that
sandboxes restored from one snapshot do not share kernel random state
([guest/kernel](../guest/kernel)).

## Tenancy and authentication

- **API keys** are per team and stored as SHA-256 hashes. Every sandbox and
  template lookup is scoped to the caller's team. The admin key is separate,
  generated by the stack and kept in Secrets Manager.
- **envd** (the agent in each sandbox) requires a per-sandbox access token for
  every call. The token is set when the sandbox starts, including after a
  restore from snapshot. The edge proxy forwards only envd's public endpoints;
  `/init` and other internal endpoints are never reachable from outside.
- **Sandbox ports** are public to anyone who can reach the load balancer and
  knows the sandbox ID, as with E2B, unless the sandbox was created with
  `allow_public_traffic=False`. Then every request needs the sandbox's traffic
  token.
- **Hosts and the egress gateway** authenticate to the control plane with
  their IAM roles: they send a signed STS `GetCallerIdentity` request that the
  control plane replays to STS. A host's identity is its instance ID (the role
  session name). The control plane accepts only the stack's own host and
  gateway roles.
- **Control plane to host**: TLS with a certificate the host generates at
  start and reports in its heartbeat; the control plane and edge pin it. Each
  call also carries a per-host bearer token.

## Data flows

| From | To | Carries | Protection |
| --- | --- | --- | --- |
| Clients | Load balancer | API calls, sandbox traffic | TLS 1.2 or 1.3 (`ELBSecurityPolicy-TLS13-1-2-2021-06`) |
| Load balancer | api and edge tasks | Same | HTTP inside private subnets, security groups |
| api and edge | Host agents | Sandbox operations, envd traffic | TLS with pinned certificates, bearer token |
| Host agents | Egress gateway | Sandbox connections with a PROXY v2 header naming the sandbox | Private subnets, security groups, source IP checked against the sandbox's host |
| Egress gateway | Internet or VPC | What the policy allows | TLS end to end, except credential hosts (below) |
| Hosts | S3 | Template and pause snapshots | Presigned URLs from the control plane, TLS, SSE-KMS |

**At rest**, the stack's customer managed KMS key encrypts DynamoDB tables,
the artifacts bucket, log groups and the ECR repository. Host volumes use
`aws/ebs` or the key you set in `HostEbsKmsKeyArn`.

**Credential hosts**: to add a header, the gateway terminates the sandbox's TLS
connection with a certificate from the stack's own egress CA, then opens a
verified TLS connection to the real host. Only hosts with a credential rule
are intercepted. The CA's private key is in Secrets Manager and readable only
by the gateway role. See [egress.md](egress.md#credential-rules).

## What leaves your AWS account

Nothing goes to Weft except the daily license check, which sends exactly four
fields: license ID, stack version, AWS Region and peak concurrent sandboxes
since the last check ([licensing.md](licensing.md)). Offline and Marketplace
licenses send nothing. There is no other telemetry, and Weft has no IAM role,
network path or support access into the stack.

Other outbound traffic is yours to control: sandbox egress (only what policies
allow), image pulls for templates built from public registries (turn off with
`HostInternetAccess=disabled`), and AWS API calls within your account.

## Supply chain

- Releases are built by `.github/workflows/release.yml` from a tag, with
  third-party actions pinned to commit SHAs and AWS access through OIDC.
- Container images are signed with cosign (keyless). SBOMs and SLSA provenance
  are attached.
- A release manifest lists the AMI per Region, image digests and the SHA-256 of
  every artifact. It is signed with Sigstore. The stack's `ReleaseVerification`
  custom resource verifies it, and the stack refuses to start services or hosts
  whose AMI, images or Lambda code differ from it.
- envd is built from a pinned upstream revision and checked against a pinned
  hash ([guest/envd](../guest/envd)). The guest kernel source is checked
  against kernel.org's signed hash list ([guest/kernel](../guest/kernel)).
- Rust `unsafe` code is denied across the workspace.

## Escape-attempt suite

[tests/escape](../tests/escape) runs attacks from inside a live sandbox and
fails if any succeeds:

- reaching instance metadata over IPv4 and IPv6, the host's addresses, the
  host agent API and other sandboxes
- connecting to the internet directly, or through UDP, ICMP or DNS
- resolving names outside the policy
- calling envd without its token, or with another sandbox's token
- (Firecracker) seeing the host kernel, `/dev/kvm`, loadable modules, other
  processes or memory beyond the sandbox's own; flooding the console; filling
  the disk

Run it against your own stack as described in
[development.md](development.md#testing-an-installed-stack).

## Known limitations

- **Verification status.** The network half of the escape suite passes
  against the development runtime. The Firecracker half has not yet run on
  real KVM; see [Project status](../README.md#project-status).
- **The development namespace runtime is not an isolation boundary.** It runs
  sandboxes as processes on the host kernel and refuses to start without
  `--insecure-namespace-runtime`. Stacks never use it.
- **Shared state from snapshots.** Userspace random state created by a
  template's start command, and the kernel `boot_id`, are the same in every
  sandbox from that template build.
- **Credential echo.** Response bodies are not scrubbed. If an upstream API
  echoes the injected credential back, the sandbox can read it.
- **Public-suffix wildcards** such as `*.co.uk` are accepted in egress
  policies.
- **Denial of service** is bounded per sandbox by cgroup and rate limits, and
  per host by `MaxSandboxesPerHost`. There is no per-team quota on the number
  of sandboxes yet; the license's concurrency cap only warns.
