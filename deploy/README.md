# Deploying Weft Sandboxes on AWS

Weft Sandboxes installs as **one CloudFormation stack in your own AWS account**.
Everything runs there: private subnets, an internal load balancer, a customer
managed KMS key, and no IAM role or network path for Weft. Nothing leaves the
account except the control plane's license check (and, if you allow it,
template image pulls from public registries).

| Path | What it is |
| --- | --- |
| [`cloudformation/weft-sandboxes.yaml`](cloudformation/weft-sandboxes.yaml) | The stack |
| [`cloudformation/functions/`](cloudformation/functions) | Lambda-backed custom resources (TypeScript, with tests) |
| [`cloudformation/scripts/render_release_template.py`](cloudformation/scripts/render_release_template.py) | Fills release values into the template at release time |
| [`packer/`](packer) | Host AMI (Packer HCL2): Firecracker, guest artifacts, host agent, systemd units, hardening |
| [`../packages/control-plane/Dockerfile`](../packages/control-plane/Dockerfile), [`../crates/egress-gateway/Dockerfile`](../crates/egress-gateway/Dockerfile) | Container images |
| [`../.github/workflows/release.yml`](../.github/workflows/release.yml) | Signed release pipeline |

Everything under `deploy/` is Apache-2.0 ([LICENSE](LICENSE)).

## Install

You need:

- **A domain** for sandboxes, such as `sandbox.example.com`. Clients use it as
  `E2B_DOMAIN`; the API is `https://api.<domain>` and every sandbox port is
  `https://<port>-<sandbox-id>.<domain>`.
- **TLS**: either a Route 53 **public hosted zone** containing the domain (the
  stack creates and DNS-validates an ACM certificate for `api.<domain>` and
  `*.<domain>`), or an existing ACM certificate covering both names.
- **A Weft license key** (or an AWS Marketplace subscription). Activating the
  license shares the release's host AMIs with your account.
- A supported Region (one the release built an AMI for; the stack checks).

Then open the release's **Launch Stack** link (on the GitHub release page), or:

```
https://console.aws.amazon.com/cloudformation/home?region=<region>#/stacks/create/review
  ?templateURL=https://weft-sandboxes-releases-<region>.s3.<region>.amazonaws.com/v<version>/weft-sandboxes.yaml
  &stackName=weft-sandboxes
```

Fill in `DomainName`, `PublicHostedZoneId` (or `CertificateArn`) and
`LicenseKey`, acknowledge IAM resource creation, and create the stack. With the
defaults it creates a new two-AZ VPC and is ready in about 12 to 15 minutes
(NAT gateways, certificate validation and the first ECS deployment dominate).

Afterwards:

```sh
# The bootstrap admin key (48 characters, generated by the stack).
aws secretsmanager get-secret-value --secret-id <AdminKeySecretArn> \
  --query SecretString --output text

# Create a team API key with the weft-sandbox CLI using the admin key, then
# give clients the stack's E2BEnvironment output:
E2B_API_URL=https://api.<domain> E2B_DOMAIN=<domain> E2B_API_KEY=<team key>
```

The domain resolves only inside the VPC (Route 53 private hosted zone). For
clients in connected networks (peering, Transit Gateway, VPN, Direct Connect),
forward the domain to a Route 53 Resolver inbound endpoint in the VPC or
associate the private zone with their VPCs. For a short evaluation you can set
`LoadBalancerScheme=internet-facing` with `PublicAllowedCidr`; the stack then
adds a second, public load balancer reachable only from that CIDR (and public
DNS records when `PublicHostedZoneId` is set).

Template images go to the stack's ECR repository (`EcrRepositoryUri`).
Operators reach hosts with SSM Session Manager only (there is no SSH):
`aws ssm start-session --target <instance-id>`.

## Architecture

```
          clients (VPC / connected networks)
                        |  HTTPS 443, api.<domain> and *.<domain>
                        v
   +---------------- internal ALB (TLS 1.2/1.3, HTTP/2, idle timeout 3600 s) ----------------+
   |  host api.<domain> -> api target group (3000)    default -> edge target group (3001)     |
   +------------------------------------------------------------------------------------------+
            |                                  |
     ECS Fargate: api (>=2)             ECS Fargate: edge (>=2)       ECS Fargate: worker (1)
            |   \                              |                              |
            |    \-- DynamoDB, S3, ECR token   |-- DynamoDB GetItem           |-- DynamoDB, S3, CloudWatch metric
            v                                  v                              v
     host agents :5007 (API)  :5008 (data-path tunnel)  <---------------------+
     EC2 Auto Scaling group, C8i/M8i/R8i with nested virtualization (or .metal)
     Firecracker microVMs; every sandbox connection -> egress gateway
            |
            |  TCP 15000, PROXY protocol v2, direct to task IPs (gateway.<InternalDomain>, Cloud Map)
            v
     ECS Fargate: egress gateway (policy + credential injection) --NAT--> allowed destinations
```

- Hosts register with the control plane at `https://api.<domain>` and
  authenticate with their IAM role (a signed STS `GetCallerIdentity` that the
  control plane replays; session name = instance ID). The egress gateway
  authenticates the same way with its task role.
- Hosts connect to gateway tasks directly (Cloud Map A records), not through a
  load balancer, because the gateway checks that a connection's source IP is
  the IP of the host running the sandbox.
- Hosts never receive S3 or ECR permissions: the control plane hands them
  presigned S3 URLs and short-lived registry tokens.

## Parameters

Required: `DomainName`, one of `PublicHostedZoneId` / `CertificateArn`, and
`LicenseKey` (with `LicenseMode=key`). Everything else has a working default.

| Parameter | Default | Meaning |

| `PublicHostedZoneId` | | Public zone for ACM DNS validation (stack creates the certificate) |
| `CertificateArn` | | Existing ACM certificate for `api.<domain>` and `*.<domain>` |
| `LicenseKey` | | Weft license key (NoEcho; stored in Secrets Manager) |
| `LicenseMode` | `key` | `key` or `marketplace` (AWS License Manager entitlement) |
| `MarketplaceProductSku` | | Marketplace product SKU (`marketplace` mode) |

| `HostInstanceType` | `c8i.2xlarge` | Primary host type (first for On-Demand) |
| `HostInstanceTypeAlt1` / `Alt2` | `m8i.2xlarge` / `r8i.2xlarge` | Spot diversification (blank for none) |
| `HostMinSize` / `HostMaxSize` | `1` / `10` | Fleet bounds |
| `HostOnDemandBaseCapacity` | `1` | Hosts always On-Demand |
| `HostOnDemandPercentageAboveBase` | `0` | On-Demand share above the base (0 = Spot) |
| `HostTargetSlotUtilization` | `70` | Target for the `SlotUtilization` metric |
| `MaxSandboxesPerHost` | `32` | `WEFT_MAX_SANDBOXES` |
| `HostDataVolumeGiB` / `Iops` / `Throughput` | `200` / `3000` / `250` | gp3 data volume for `/var/lib/weft` |
| `HostDisableSmt` | `true` | SMT off on hosts (Firecracker multi-tenant guidance; halves vCPUs) |

| `RetainBucketsOnDelete` | `false` | Keep the artifacts bucket and its KMS key on deletion |
| `LogRetentionDays` | `365` | Retention for every log group |
| `AccessLogsBucketName` | | Existing SSE-S3 bucket for ALB and S3 access logs |
| `PermissionsBoundaryArn` | | Permissions boundary for every role the stack creates |
| `HostAmiId`, `ControlPlaneImage`, `GatewayImage` | release values | Mirrors only; must still match the signed manifest |
| `ReleaseBucketPrefix` | `weft-sandboxes-releases` | Release artifacts come from `s3://<prefix>-<region>/v<version>/` |

The template's `Rules` reject inconsistent combinations before anything is
created (missing certificate source, missing license key, public ALB without
an allowlist or with 0.0.0.0/0, existing VPC without subnets, unsupported
Region). The `NetworkPreflight` custom resource then checks what CloudFormation
cannot: subnets belong to the VPC and span two AZs, the VPC has DNS support and
hostnames, the slot pool does not overlap any VPC CIDR and has room for
`MaxSandboxesPerHost`, and every host type is x86_64 and either reports the
`nested-virtualization` processor feature or is bare metal (matching
`HostVirtualization`).

## What the stack creates, and why

**Release verification (`ReleaseVerification`, custom resource).** Before any
compute exists, the `verify-release` Lambda reads
`release-manifest.json` and its Sigstore bundle from the release bucket and
verifies the signature with sigstore-js against the Sigstore trusted root that
the release bundled into the function (no network call to Sigstore). The
signing certificate must carry exactly the GitHub Actions OIDC identity
`https://github.com/weftsh/byoc/.github/workflows/release.yml@refs/tags/v<version>`
(issuer `https://token.actions.githubusercontent.com`) and be logged in Rekor.
Only then does it compare the manifest with what the stack will run: the host
AMI for this Region, the control-plane and gateway image digests (images must
be pinned by digest; a mirror is fine if the digest matches), and the SHA-256
of every deployed custom-resource Lambda (`CodeSha256`). Any mismatch fails the
stack before the ECS services, the Auto Scaling group or the egress CA exist.
It re-runs on every stack update.

*Trust model.* The verifier itself is Lambda code from the release bucket, so
it cannot vouch for itself: what it guarantees is that the running release is
the signed one and that no parameter or mirror swapped an AMI, image or
function. To anchor trust independently, verify the release before installing
(the release page shows the `cosign verify-blob` command) and, if you want,
mirror the template, manifest and functions into your own buckets
(`ReleaseBucketPrefix`). Every artifact also has SLSA build provenance
(`gh attestation verify`).

**Network.** A VPC with public subnets (NAT gateways; the optional public ALB)
and private subnets (everything else), or your existing VPC. S3 and DynamoDB
gateway endpoints are always created in a new VPC; interface endpoints are
optional. Security groups:

| Group | Inbound | Outbound |
| --- | --- | --- |
| Internal ALB | 443 from `ClientCidr`, hosts, gateway | 3000 to api, 3001 to edge |
| Public ALB (optional) | 443 from `PublicAllowedCidr` | 3000 to api, 3001 to edge |
| api | 3000 from ALBs | 443 (AWS APIs, image pulls, license check), 5007-5008 to hosts |
| edge | 3001 from ALBs | 443, 5007-5008 to hosts |
| worker | none | 443, 5007 to hosts (stops expired sandboxes) |
| egress gateway | 15000 from hosts | TCP to anywhere: it enforces each sandbox's allowlist and never connects to link-local or metadata addresses |
| hosts | 5007-5008 from api and edge; 5007 from worker | 443 to the ALB, 15000 to the gateway, 53 and 443 to the VPC (resolver, endpoints), 443 to the S3 prefix list; 443 to the internet only with `HostInternetAccess=enabled` |
| interface endpoints | 443 from the VPC | none |

**Data.** Seven DynamoDB tables (`<stack>-teams`, `-apikeys`, `-templates`,
`-builds`, `-sandboxes` with `teamId-index`, `-hosts`, `-meta`): on-demand,
KMS CMK, point-in-time recovery. An S3 bucket for `templates/` and
`snapshots/`: SSE-KMS with the CMK and bucket keys, versioning, block public
access, bucket-owner-enforced, TLS 1.2+ only, incomplete multipart uploads
aborted after 1 day, noncurrent versions expired after 7 days. An ECR repository
for template images: KMS, scan on push, untagged images expire after 14 days.
Three Secrets Manager secrets (admin key, license key, egress CA) with the CMK.
One KMS key (rotation on) for all of it and for every log group.

**Egress CA (`EgressCa`, custom resource).** Generates an ECDSA P-256 CA
(self-signed, 10 years, `CN=Weft Sandboxes egress CA <stack>`, `CA:TRUE,
pathlen:0`, key usage certificate and CRL signing) at creation and writes
`{"certPem","keyPem"}` to the CA secret. The secret's resource policy denies
`GetSecretValue` to everyone but the gateway task role, and `PutSecretValue` to
everyone but the CA function, whose role cannot read it. The certificate (not
the key) goes to the control plane as `WEFT_EGRESS_CA_CERT` and to the SSM
parameter `/weft/<stack>/egress-ca-cert`. The CA is kept across updates and
deleted with the stack.

**Control plane.** One ECS cluster (Container Insights on) with four Fargate
services: api (port 3000, `GET /health`), edge (3001, `GET /healthz`, 120 s to
drain long-lived connections), worker (exactly one task, never two during
deployments) and the egress gateway (15000; registered in Cloud Map as
`gateway.<InternalDomain>`). All containers run as non-root with a read-only
root filesystem, all capabilities dropped and deployment circuit breakers on.

**Load balancing and DNS.** An internal ALB with an HTTPS listener
(`ELBSecurityPolicy-TLS13-1-2-2021-06`, HTTP/2, invalid headers dropped, 3600 s
idle timeout): `api.<domain>` goes to api, everything else to edge. A Route 53
private hosted zone for the domain with `api.<domain>` and `*.<domain>` aliases.

**Hosts.** A launch template (IMDSv2 required, hop limit 1, no key pair,
encrypted gp3 volumes, `CpuOptions.NestedVirtualization: enabled` unless
`metal`) and an Auto Scaling group: Spot first with On-Demand base capacity
(`price-capacity-optimized`, capacity rebalancing), target tracking on the
worker's `SlotUtilization` metric (namespace and `StackName` dimension both
equal to the stack name, so installs never share a metric). User data writes only
stack settings to `/etc/weft/stack.env`; the AMI does the rest (below).

### Runtime settings passed to the application

Control plane tasks (all three roles): `WEFT_ROLES`, `WEFT_DOMAIN`,
`AWS_REGION`, `WEFT_VERSION`, `WEFT_STORE=dynamodb`,
`WEFT_TABLE_PREFIX=<stack>-`, `WEFT_INTERNAL_AUTH=aws-iam`,
`WEFT_SERVER_ID=<stack>`, `WEFT_AWS_ACCOUNT_ID`, `WEFT_HOST_ROLE_NAME`,
`WEFT_GATEWAY_ROLE_NAME`, `WEFT_LICENSE_MODE` (+ `WEFT_MARKETPLACE_PRODUCT_SKU`).
api and worker also get `WEFT_ARTIFACTS_BUCKET`, `WEFT_BOOTSTRAP_TEMPLATES`,
`WEFT_METRICS_NAMESPACE=<stack>`, `WEFT_ECR_REGISTRY`, `WEFT_EGRESS_CA_CERT`
and the secrets `WEFT_BOOTSTRAP_ADMIN_KEY` and `WEFT_LICENSE_KEY` (key mode).
The edge gets no license key: it does not enforce the license, and without one
its startup only reads the license state.

Egress gateway: `WEFT_CONTROL_PLANE_URL=https://api.<domain>`,
`WEFT_SERVER_ID=<stack>`, `AWS_REGION`, `WEFT_CA_SECRET_ID=<CA secret ARN>`.

Hosts (`/etc/weft/host-agent.env`): `WEFT_HOST_ID` (instance ID),
`WEFT_PRIVATE_IP`, `WEFT_CONTROL_PLANE_URL`, `WEFT_AUTH=aws-iam`,
`WEFT_SERVER_ID`, `AWS_REGION`, `WEFT_EGRESS_GATEWAY=gateway.<InternalDomain>:15000`,
`WEFT_RUNTIME=firecracker`, `WEFT_MAX_SANDBOXES`, `WEFT_SLOT_POOL`, plus the
data, guest, kernel, Firecracker and jailer paths.

## IAM

Every role is created by the stack, trusts one AWS service (with
`aws:SourceAccount`/`aws:SourceArn` conditions where the service supports
them), takes the optional permissions boundary, and is commented statement by
statement in the template. There is no cross-account trust, no vendor role,
and no `*` action.

| Role | Used by | Allowed |
| --- | --- | --- |
| `ControlPlaneTaskRole` | api and worker tasks | Item read/write on the seven tables and the GSI (no table administration); get/put/delete objects and abort multipart uploads in the artifacts bucket, list it (presigned URLs for hosts); the CMK only through DynamoDB, S3 and ECR; `ecr:GetAuthorizationToken` and pull on the template repository (tokens handed to hosts carry these permissions, so hosts can pull only that repository); `cloudwatch:PutMetricData` in the stack's own namespace only; License Manager checkout in marketplace mode only |
| `EdgeTaskRole` | edge tasks | `dynamodb:GetItem` on the sandboxes and hosts tables, and on the `license` item of the meta table (the shared startup reads it); decrypt through DynamoDB |
| `GatewayTaskRole` | egress gateway | `GetSecretValue` on the CA secret and on secrets tagged `weft-sandbox-access=true`; `kms:Decrypt` only through Secrets Manager; explicit deny on the stack's admin and license secrets |
| `ControlPlaneExecutionRole` | ECS agent for control plane tasks | Write the control plane log group; read the admin and license secrets for injection; ECR pull only when an image mirror is configured |
| `GatewayExecutionRole` | ECS agent for gateway tasks | Write the gateway log group; ECR pull only for mirrors |
| `HostRole` | EC2 hosts | `AmazonSSMManagedInstanceCore` (Session Manager); write the hosts log group; explicit deny on Parameter Store reads (which the managed policy would allow). No S3, ECR, DynamoDB or Secrets Manager |
| `VerifyReleaseRole` | verify-release Lambda | Read `s3://<release bucket>/v<version>/*`; read-only EC2 `Describe*` (images, instance types, VPCs, VPC attributes, subnets, prefix lists; these have no resource-level permissions); `GetFunctionConfiguration` on the stack's three functions |
| `EgressCaRole` | egress-ca Lambda | `PutSecretValue` on the CA secret (cannot read it); encrypt through Secrets Manager; put/get/delete the one CA certificate parameter |
| `CleanupRole` | cleanup Lambda | List, delete objects and versions, abort uploads, set lifecycle and delete, on the artifacts bucket only; `ScheduleKeyDeletion` on the stack key |
| `FlowLogsRole` (optional) | VPC Flow Logs | Write the flow log group |

The CMK's key policy has the standard account statement (so the IAM policies
above govern its use) and lets CloudWatch Logs use it for this account's log
groups only. Host EBS volumes use `aws/ebs` unless `HostEbsKmsKeyArn` is set:
a stack-created CMK would have to name the Auto Scaling service-linked role,
which does not exist yet in a new account.

## Host AMI (`deploy/packer`)

**Base: Amazon Linux 2023** (x86_64, kernel 6.12) rather than Ubuntu 24.04:
it is maintained by AWS with the SSM agent, CloudWatch agent and EC2 utilities
in its own repositories; its versioned repositories make an image reproducible
from the same release version (the build moves to the newest release and locks
`dnf` to it); its 6.12 kernel has KVM, tap, veth, nftables and XFS reflink;
it is supported to 2029; and it is what AWS-centric security reviews already
approve. Ubuntu would work too, but adds snap-packaged agents and unattended
upgrades to reason about.

The build installs Firecracker and jailer (version and three SHA-256s pinned in
`firecracker.auto.pkrvars.hcl`: the release archive, the firecracker binary and
the jailer binary, plus the archive's own `SHA256SUMS`), the guest kernel,
`envd` and `weft-guest-init` in `/opt/weft/guest/`, `weft-host-agent` in
`/usr/local/bin/`, and `iproute`, `iptables-nft`, `e2fsprogs` (checked to be
at least 1.43 for `mkfs.ext4 -d`), `xfsprogs`, `util-linux`, `nvme-cli`,
`mdadm`, `amazon-cloudwatch-agent`. Every Weft input is verified against the
SHA-256 the release workflow computed when it built it.

Units and scripts:

- `weft-data-volume.service` formats (only an empty device) and mounts
  `/var/lib/weft` as XFS with `reflink=1`: the instance's NVMe instance store
  when it has any (RAID 0 across several), otherwise the gp3 data volume at
  `/dev/sdf`. Mounted `noatime,nosuid` (not `nodev`/`noexec`: the jailer
  creates device nodes and runs Firecracker from its chroot there).
- `weft-host-tuning.service` applies the non-sysctl parts of Firecracker's
  [production host setup](https://github.com/firecracker-microvm/firecracker/blob/main/docs/prod-host-setup.md)
  on every boot: swap off, KSM off, SMT off (unless `HostDisableSmt=false`),
  KVM module and `/dev/kvm` check, cgroup v2 `favordynmods`, and
  `kvm.nx_huge_pages=never` only on CPUs not affected by iTLB multihit.
- `weft-host-bootstrap` (from user data, first boot) validates
  `/etc/weft/stack.env`, reads the instance ID and private IP from IMDSv2,
  writes `/etc/weft/host-agent.env` (0600), configures the CloudWatch agent for
  the stack's hosts log group, and starts `weft-host-agent.service`
  (`/usr/local/bin/weft-host-agent run`, root, `Restart=always`).

Hardening: sshd and EC2 Instance Connect removed (SSM only), no SSH keys from
cloud-init, root locked; no swap; no core dumps (a Firecracker core would
contain guest memory); `/dev/kvm` limited to root and `kvm`; `kvm_intel
nested=0` (microVMs never get VMX); unused protocols and filesystems blocked;
host IP forwarding off (the host never routes sandbox traffic; slot namespaces
enable it for themselves); kernel and network sysctls (`kptr_restrict`,
`dmesg_restrict`, unprivileged BPF off, `ptrace_scope=2`, strict reverse path
filtering, no redirects); kernel console logging limited (`quiet loglevel=1`);
bounded journald; the AMI defaults to IMDSv2. SELinux stays in the AL2023
default (permissive); the jailer provides per-VM isolation (chroot,
namespaces, seccomp, cgroups, one unprivileged UID per VM).

The AMI is unencrypted so it can be shared; the launch template encrypts every
volume at launch. AMIs are private: Weft's license service grants launch
permission to licensed accounts, the release workflow never does.

Build locally:

```sh
packer init deploy/packer
packer build -var version=1.2.3 \
  -var host_agent_path=dist/bin/weft-host-agent -var host_agent_sha256=$(sha256sum dist/bin/weft-host-agent | cut -d' ' -f1) \
  ... deploy/packer      # see the header of deploy/packer/weft-host.pkr.hcl
```

## Operating

- **Upgrades**: update the stack with the new release's template URL. The
  release is verified again first; ECS services roll with circuit breakers.
  A new AMI updates the launch template only: existing hosts keep running
  their sandboxes. Replace them in a maintenance window with an instance
  refresh (`aws autoscaling start-instance-refresh --auto-scaling-group-name
  <HostAutoScalingGroupName> --preferences MinHealthyPercentage=90,InstanceWarmup=300`).
- **Scaling**: the worker publishes `SlotUtilization` (percent of sandbox slots
  in use across the fleet); target tracking adds hosts above the target and
  removes them below it. Scale-in and Spot interruptions terminate a host's
  running sandboxes; keep `HostMinSize` and `HostOnDemandBaseCapacity` at your
  baseline.
- **Logs**: `/weft/<stack>/control-plane` (streams `api/`, `edge/`, `worker/`),
  `/weft/<stack>/egress-gateway` (includes the egress audit log),
  `/weft/<stack>/hosts` (`<instance-id>/host-agent`, `<instance-id>/bootstrap`),
  `/weft/<stack>/functions/*`, optional `/weft/<stack>/vpc-flow-logs`.
- **Sandbox credentials**: tag a Secrets Manager secret
  `weft-sandbox-access=true` to let the egress gateway inject it into allowed
  API calls. Encrypt it with `aws/secretsmanager` or a CMK whose key policy
  lets the gateway role decrypt through Secrets Manager.

## Uninstall

Delete the stack. CloudFormation first removes the ECS services and the Auto
Scaling group (they depend on the `Cleanup` custom resource), then `Cleanup`
runs:

- `RetainBucketsOnDelete=false` (default): it sets an expire-everything
  lifecycle rule as a fallback, deletes every object version, delete marker and
  unfinished multipart upload, deletes the bucket, and schedules the KMS key for
  deletion (7-day waiting period, cancellable with `aws kms cancel-key-deletion`).
- `RetainBucketsOnDelete=true`: it does nothing; the artifacts bucket and the
  KMS key that encrypts it are left in place (shown as `DELETE_SKIPPED`).

Everything else the stack created is deleted by CloudFormation: tables (with
their point-in-time recovery data), secrets, log groups, the ECR repository
(with its images), the egress CA and its SSM parameter, load balancers,
certificate, hosted zones, Cloud Map namespace, VPC and endpoints, IAM roles and
Lambda functions. If stack creation fails, the rollback deletes the bucket and
key as well (`DeletionPolicy: RetainExceptOnCreate`).

Left behind by design: the ACM DNS validation CNAME records in your public
zone (CloudFormation does not remove them; they are harmless), and the
account-wide service-linked roles AWS creates on first use of ECS, ELB, Auto
Scaling and Spot. If the bucket holds more objects than the cleanup function
can delete in its 15 minutes, the stack still deletes cleanly, the bucket is
left with the expire-everything rule, and the key is not scheduled; delete both
once the bucket is empty.

## Releases (`.github/workflows/release.yml`)

On a `v*` tag, with least-privilege job permissions and third-party actions
pinned to full commit SHAs:

1. **Preflight**: tag, `Cargo.toml` and `package.json` versions agree; the
   repository is the one the verifier trusts; **fails if
   `packages/license/src/trusted-keys.ts` has an empty
   `RELEASE_SIGNING_KEYS`**.
2. **Test**: TypeScript build, typecheck and tests; `cargo fmt --check`,
   `clippy -D warnings`, `cargo test`; Lambda tests; `cfn-lint`; `shellcheck`.
3. **Binaries**: `weft-guest-init` (static musl), `weft-host-agent` (built in
   Amazon Linux 2023 for glibc compatibility), `envd` (`guest/envd/build.sh`,
   which checks its pinned hash), the guest kernel (`guest/kernel/build.sh`);
   SPDX SBOM; SLSA build provenance (`actions/attest-build-provenance`).
4. **Images**: control plane and gateway pushed to `ghcr.io/weftsh/`,
   `cosign sign` (keyless), SPDX SBOM attached as a signed `cosign attest`
   attestation, SLSA provenance pushed to the registry.
5. **Functions**: tests, Sigstore trusted root fetched through TUF, esbuild
   bundles zipped reproducibly, provenance.
6. **AMI**: Packer build in the first Region and private copies to the others,
   with AWS access through OIDC (`vars.RELEASE_ROLE_ARN`), never static keys.
7. **Publish**: render the template with the AMI map, image digests and
   version (`render_release_template.py`, then `cfn-lint` again); write
   `release-manifest.json` (version, AMI per Region, image digests, SHA-256 of
   every artifact); `cosign sign-blob --bundle` keyless, verified immediately
   with the expected identity; upload to every Region's release bucket (refusing
   to overwrite an existing version; manifest and signature last); GitHub
   release with Launch Stack links, SBOMs and checksums.

Release infrastructure (outside this repository): per-Region buckets
`<prefix>-<region>` with public read of `v*/` objects (CloudFormation, Lambda and
customer stacks read them), versioning and ideally S3 Object Lock; an IAM role
trusting `token.actions.githubusercontent.com` for
`repo:weftsh/byoc:environment:release`, allowed to run the Packer build (EC2
instances, images, snapshots, temporary security groups and key pairs in the
build Region, `CopyImage` to the others) and to put objects in the release
buckets; the `release` environment with required reviewers; and a tag ruleset
so only maintainers can create `v*` tags, since a tag's workflow run is what
the stacks trust.

## Development

```sh
# Custom-resource Lambdas (own lockfile, separate from the app workspace)
cd deploy/cloudformation/functions && pnpm install && pnpm run typecheck && pnpm test

# Template
pip install cfn-lint checkov
cfn-lint --include-checks I -- deploy/cloudformation/weft-sandboxes.yaml
checkov -f deploy/cloudformation/weft-sandboxes.yaml

# Host image
packer init deploy/packer && packer validate -syntax-only deploy/packer
shellcheck -x deploy/packer/scripts/*.sh deploy/packer/files/bin/*

# Workflow
actionlint .github/workflows/release.yml
```

Suppressed findings are justified inline: `Metadata: checkov: skip` and
`Metadata: cfn-lint: config: ignore_checks` in the template, `checkov:skip`
comments in the Dockerfiles.
